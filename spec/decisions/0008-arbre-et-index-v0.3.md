# 0008 — LeanIMT, versions et index de chemins

Statut : adopté pour v0.3. Références : §§4.2, 5, 7.2, 12, 14.3.

Le hash interne est le Poseidon à deux entrées utilisé par `poseidon-lite 0.3.0`, comparé à `go-iden3-crypto v0.0.17`. `poseidon2` est ici le nom de la fonction à deux entrées de `poseidon-lite`, pas une substitution par l’algorithme Poseidon2. La structure suit `@zk-kit/lean-imt 2.2.5`, verrouillé transitivement par npm.

Le LeanIMT a une profondeur dynamique `ceil(log2(size))`, sans hachages de remplissage. Un parent qui n’a qu’un enfant propage sa valeur sans hash. Le chemin n’inclut pas les frères absents ; son `index` contient seulement les bits des niveaux effectivement hachés et peut différer de l’index physique. L’API publie les deux : `leaf_index` et `index`. Le client vérifie leur correspondance, les frères, la feuille, la racine et les métadonnées avant toute génération de preuve. Il transmet au SDK une copie des frères, car le SDK complète ce tableau en place pour le circuit.

La capacité de circuit est de 2^16 ou 2^26 positions, retraits compris. L’inscription ajoute une feuille non nulle. Une rotation d’identité met à zéro l’ancienne position et ajoute le nouvel engagement en fin d’arbre. Une rotation de clés qui conserve l’engagement garde la position. Un retrait met à zéro la position courante ; une position retirée n’est jamais réattribuée. Les engagements restent réservés par le registre des comptes. Le nombre actif est distinct du nombre de positions. Un arbre sans position a une racine null ; un arbre qui conserve des positions toutes retirées garde sa racine mathématique et `active_count:"0"`.

Deux arbres ont des rôles distincts. Le groupe d’ouverture `inline_dev` conserve l’ordre trié par `account_id` du §7.2 et omet les comptes inactifs. L’arbre incrémental des comptes conserve l’ordre d’exécution et les positions retirées, conformément au §14.3. Le fournisseur local réel sait construire le premier ; la nouvelle configuration `eligibility` active le second. La profondeur 26 et son banc de capacité ne rendent pas encore le registre principal ou les partitions `scale_1` disponibles.

La configuration optionnelle contient `circuit_depth` et `suite_id`. Elle exige un module d’éligibilité actif. Le compte publie son `eligibility_index` courant. La table `eligibility[index]` conserve toutes les feuilles, y compris zéro. `network["config"].eligibility` contient le domaine, la hauteur, la racine, les comptes et la profondeur de l’instantané courant. Ces valeurs sont engagées dans `AppHash` et écrites atomiquement avec les comptes. L’absence de cette configuration préserve les formats et racines v0.1/v0.2. Une suite révoquée bloque les opérations de compte qui nécessiteraient son arbre, sans repli implicite.

Les métadonnées portent `network_id`, `protocol_epoch`, `tree_id`, `suite_id`, `height`, `circuit_depth`, `size`, `active_count`, `root`. Leur identifiant est `D("eligibility/snapshot",[network_id,protocol_epoch,tree_id,suite_id,height,circuit_depth,size,active_count,root])`. Cet identifiant contrôle la cohérence et le domaine, pas l’authenticité du registre. Les réponses de chemins incluent ces métadonnées, la feuille, les deux index et les frères. Tous les entiers applicatifs sont des chaînes.

Le registre déterministe garde un arbre pur, copié avant une transition candidate. L’index de service est séparé. `eligibilityindex.Sync` le reconstruit depuis les transactions d’un journal local déjà rejoué et vérifié, et impose à chaque hauteur la même racine et les mêmes métadonnées que l’état du registre. Un écart annule la transaction d’indexation avant publication. La reprise revérifie aussi le préfixe déjà indexé. Les rotations et retraits multiples dans un même bloc sont rejoués dans leur ordre. Une migration d’epoch ou de domaine d’index n’est pas improvisée ; elle exige un traitement versionné ultérieur.

L’index durable combine une base de niveaux immuables et des versions de nœuds dans bbolt 1.4.3. Les clés des deltas sont `(level,index,height)` en ordre binaire réseau. Une lecture à H choisit la dernière version au plus à H, sinon le nœud de base. Les nœuds, métadonnées et curseur sont mis à jour dans la même transaction. Chaque valeur écrite possède son propre tableau d’octets : le hash du parent ne peut pas réutiliser une tranche encore référencée par bbolt. Les anciennes versions sont conservées sans élagage à v0.3.

L’import massif construit les niveaux en O(n) hachages avec mémoire de travail bornée, synchronise les fichiers et publie le manifeste en dernier. Chaque niveau a taille et SHA-256 ; le redémarrage les contrôle. Les valeurs hors champ sont refusées. Les fichiers incomplets ne sont pas des instantanés publiés. Ce parcours sert aux fixtures et aux imports authentifiés par leur appelant ; il n’est pas une route d’inscription publique.

L’API est en lecture seule, sans cookie ni route donnant la liste des engagements. La CLI de développement écoute uniquement sur loopback. Les chemins sont vérifiables mais ne remplacent pas une preuve de finalité. Le client reçoit la référence attendue depuis le registre de confiance, puis compare tous ses champs. Le transport HTTP ne décide ni de l’ouverture ni de l’admissibilité.

Les tests tuent réellement un processus avant les métadonnées, avant le curseur et après le commit de l’index. Cinq points supplémentaires du journal principal couvrent une rotation avec arbre. Ces tests complètent les vingt scénarios antérieurs. Le contrat reste un écrivain par répertoire et la mort de processus ; la panne électrique Windows et la réplication BFT ne sont pas qualifiées ici.
